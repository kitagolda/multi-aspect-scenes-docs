Group 05 — Same Tree & FSM, >5 Nodes Differ

Count
64 landscape groups (4.8% of 1,347)
Difficulty
Medium
Target outcome
Collapse to 1 scene.object.tsx emitting the shared JSX tree once + a compact generated per-aspect property override table keyed by flatIndex or node Id.

#1. What Defines This Group

Every landscape variant still has the exact same node hierarchy and identical FSM counts, so flatIndices align 1:1 across aspects. However, 6 to 20+ child nodes have custom per-aspect Position, Scale, Bounds, Origin, Skew, Scissor, TouchArea, DrawOrder, or layout properties.

#Why does this happen in WBIP?

Full-screen arenas, lobbies, and complex multi-panel popups don't just uniformly scale down on 4x3 or widen on 19.5x9 — designers individually reposition and rescale each HUD block (header, timer, purchase panel, progress bar, board area, close button) so every widget stays legible and fills the aspect ratio comfortably.

#3. Potential Solution (Reduce to 1 Scene)

Inlining 15–30 byAspect(...) calls directly into JSX attributes would clutter the readable tree. Instead, separate structure from aspect layout overrides:

  1. Emit the shared JSX tree once (canonical 3x2 baseline) with export const sceneName = "<baseScene>";.
  2. Generate a compact typed aspect override table keyed by flatIndex (or node Id when unique), containing only the properties that actually differ from the baseline.
  3. Apply overrides via a runtime helper (applyAspectOverrides(root, ASPECT_OVERRIDES)) once inside build() and again on Game.instance.viewPortChanged.
  4. Over time, during manual feature polish, repetitive overrides (e.g. edge-anchored headers or flex rows) can be progressively replaced with @pixi/layout / ScreenAlignmentNode without changing the single-file structure.
TSX 
export const sceneName = "sceneDashesArena3x2.object";

const ASPECT_OVERRIDES: AspectOverrides = {
    "4x3": {
        10: { Scale: { x: 0.678, y: 0.678 } },
        11: { Position: { x: 119, y: 71 }, Scale: { x: 0.678, y: 0.678 } },
        12: { Position: { x: 650, y: 30 }, Scale: { x: 0.678, y: 0.678 } },
        13: { Position: { x: 396, y: 15 }, Scale: { x: 0.678, y: 0.678 } },
        31: { Position: { x: 298, y: 62 }, Scale: { x: 0.678, y: 0.678 } },
        32: { Bounds: { x: 0, y: 0, width: 853, height: 394 }, Position: { x: 53, y: 145 } },
    },
};

export function build(contentManager: IContentManager, prefabData: IPrefabData): GameComponent {
    const root = (
        <ControlNode Id="dashesArenaScreen">
            {/* ...single clean JSX tree at 3x2 baseline... */}
        </ControlNode>
    );
    applyAspectOverrides(root, ASPECT_OVERRIDES);
    return root;
}

#Edge cases & gotchas

  • Resetting back to baseline on resize: When resizing from 4x3 back to 3x2, applyAspectOverrides must restore the baseline values for any property overridden in 4x3 (snapshot initial values lazily before first override).
  • FSM-animated properties: If an overridden node also has FSM actions targeting the same property, check whether the FSM keyframes overwrite the override on state enter (if so, those scenes usually already show up in Group 06).
  • Code-behind findById reads: Because applyAspectOverrides runs synchronously inside build(), any view code reading node.position or node.boundingRect immediately after SceneBuilder.buildScene() sees the exact aspect-adjusted values.
