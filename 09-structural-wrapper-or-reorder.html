Group 09 — Structural: Same Node Count, Sibling Reorder or Wrapper-Type Swap

Count
65 landscape groups (4.8% of 1,347)
Difficulty
Medium–Hard
Target outcome
Normalize wrapper type or unify sibling layer order / DrawOrder to collapse into 1 scene.object.tsx (with FSM binding verification).

#1. What Defines This Group

Every landscape variant has the exact same total node count, yet a positional tree comparison detects node-type mismatches. Inspecting the actual WBIP trees reveals two distinct sub-cases:

  1. Sub-case 9a — Wrapper / node-type swap (6 groups): The exact same node at the exact same position in the tree swaps between compatible container types (CONTAINER_NODE ↔ RENDER_STATES_NODE) while keeping identical children.
  2. Sub-case 9b — Sibling / Flash layer reordering (59 groups): The exact same child subtrees exist under the same parent, but an artist dragged a layer up or down in Flash on one aspect ratio (e.g. moving timerAnimStates above contentAnimStates, or closeBtn above winCoinsAmount). Because WBIP serializes children in layer order, reordering siblings shifts their flatIndices and makes a naive index-by-index diff look like type swaps!

#3. Potential Solution (Reduce to 1 Scene)

  1. For Sub-case 9a (pure wrapper-type swap):
    • Normalize the node to the richer type (RenderStatesNode instead of ContainerNode, or ButtonNode instead of ControlNode after verifying Binder expectations). flatIndices remain unchanged, so the scene collapses immediately into 1 scene.object.tsx.
  2. For Sub-case 9b (sibling layer reordering):
    • Match children by Id (and subtree signature for unnamed nodes) instead of raw child index inside the wbip-processor diff engine.
    • Pick one canonical child order (e.g. 3x2) so flatIndices are locked to a single canonical tree and 1 WbipSceneV3 is kept.
    • If the layer swap actually affects visual overlap on one aspect (check bounding-box intersection), express it via DrawOrder={byAspect({ "16x9": ..., default: ... })} instead of reordering JSX children — preserving flatIndices while still honoring per-aspect paint order!
TSX 
// Keep canonical child order (stable flatIndices) and adjust paint order via DrawOrder if needed:
<ControlNode Id="challengeContent">
    <ControlNode Id="itemBgHolder" Position={byAspect({ "16x9": { x: -53, y: 20 }, default: { x: 27, y: 65 } })} />
    <ControlNode Id="contentAnimStates" /* ... */ />
    <ButtonNode Id="centralBtn" /* ... */ />
    <ControlNode
        Id="timerAnimStates"
        DrawOrder={byAspect({ "16x9": 1, default: 3 })}
        Position={byAspect({ "16x9": { x: 397, y: 138 }, default: { x: 409, y: 167 } })}
    />
    {/* ... */}
</ControlNode>

#Edge cases & gotchas

  • DrawOrder vs Pixi render order: In @playtika/pixi, DrawOrder maps to zIndex (and enables sortableChildren on the parent) — verify sibling nodes without explicit DrawOrder don't unexpectedly jump layers when sortableChildren turns on.
  • children[i] indexing in code-behind: Check if legacy view code accesses parent.children[1] by numeric index instead of findById(...) before unifying child order.
  • FSM re-indexing: Because reordering children shifts flatIndices, always use the canonical aspect's WbipSceneV3 FSM (do NOT pair 16x9's FSM with 3x2's child order without remapping node indices!).
